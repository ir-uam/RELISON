Each piece is created by a node of the graph at a given timestamp. When at least one piece is
                                        defined here, it replaces the automatic seeding for the simulation. Each feature parameter is its own column
                                        (add one with Add feature column); a cell holds that parameter's value:weight; … (weight optional).
                                        Upload/download of pieces is tab-separated. Download writes id ⇥ creator ⇥ timestamp ⇥ features, packing every feature into the last column as
                                        param=value:weight; …. Upload accepts that, and also one column per feature: give it a header such as
                                        id ⇥ creator ⇥ timestamp ⇥ feat:topic ⇥ feat:lang (the feat: prefix is optional) and each column holds that parameter's value:weight; …, just like the table's cells.
                                        Upload ▾ → Piece features loads a separate file of infoId ⇥ featureId lines (optional third column = weight); an infoId ⇥ name header names the
                                        feature, otherwise you are asked for it. Feature metrics run over these piece features and over node attributes / communities (as user features).

                                        given timestamp in the real scenario — not necessarily a piece they own. Upload/download is tab-separated

                                        real-propagation metrics (recall / precision / F1 vs. the ground truth). Records whose user isn't a node or whose piece isn't a defined piece are ignored at run time.
